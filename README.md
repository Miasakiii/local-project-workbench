# 本地项目工作台（Local Project Workbench）

> 让每个本地项目拥有一个可阅读、可操作、可继续工作的首页。

结合资源管理器的文件操作、GitHub 式仓库首页与项目专属终端，用于登记、浏览和继续本地项目。项目始终留在原位置，应用不复制、不上传源码，不自动扫描整台电脑。

## 设计边界

### 已确认需求

| 编号 | 内容 |
|---|---|
| C01 | Windows 优先 |
| C02 | 用户主动打开并登记项目目录，重启后可找回 |
| C03 | GitHub 式首页与 README 阅读 |
| C04 | 只读预览 + 外部编辑器打开 + 基础文件管理 |
| C05 | 内置真实交互式终端 |
| C06 | 读取 Git 并反映文件与代码变化 |
| C07 | GitHub 仅作为页面体验参考，不引入账号与托管功能 |
| C08 | 普通目录亦可登记为项目，Git 为可选增强能力 |

C06 的当前工作解释：**只读 Git 集成** —— 展示分支、状态与差异，不提供提交、拉取、推送、切换分支按钮；用户仍可在终端自行执行 Git 命令。

C08 的含义：**「项目」定义为已登记的本地目录，而非 Git 仓库。** 目录不是仓库、或 Git 程序不可用时，浏览、文件管理、README 阅读与终端四项能力全部保留。

### 第一版明确不做

云同步、GitHub 登录、Issues／PR、团队权限、完整代码编辑与调试、插件市场、自动运行项目脚本、整盘项目发现。

## 技术栈

**尚未锁定，当前建议 Electron + React + TypeScript。**

依据：本项目权重最高的技术难点是真实终端（PTY），node-pty 在该项上具备成熟方案；Electron 的隔离短板属「已知且可配置」范畴，有官方安全指南可循。**改用 Tauri 的触发条件**（分发体积成为硬性约束，或具备 Rust 能力并看重声明式权限模型）与完整对比见[设计稿 8.2](docs/design/本地项目管理器-设计讨论稿-v0.2.md)。

**最终结论须在 M0 技术验证获得实测数据后复核**，而非仅凭框架标签决定。

### 开发环境基线

- Git 2.55（已验证可用）
- Node.js 22.x / 24.x
- 目标平台：Windows 10 / 11
