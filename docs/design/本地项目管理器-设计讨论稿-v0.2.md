## 1. 产品定位与需求边界

**一句话定位：让每个本地项目拥有一个可阅读、可操作、可继续工作的首页。** 借鉴 GitHub 的仓库信息组织方式，结合资源管理器的文件操作与项目专属终端；不把第一版扩展为完整 IDE 或 Git 托管客户端。

核心路径：用户打开目录 → 登记为项目 → 阅读 README 与浏览文件 → 查看变化 → 使用外部编辑器或终端继续工作。项目留在原位置，应用不复制、不上传源码，不自动扫描整台电脑。

### 1.1 已确认需求

| 编号 | 已确认内容 | 产品含义 |
|---|---|---|
| C01 | Windows 优先 | 首先做好本机路径、文件操作和终端体验 |
| C02 | 用户打开并记录仓库 | 手动选择目录；重启后仍可找回项目 |
| C03 | GitHub 式首页与 README | 项目有概览、文件列表和介绍文档 |
| C04 | 只读预览、外部编辑器、基础文件管理 | 能查看内容与操作文件，但暂不内置代码编辑器 |
| C05 | 内置终端 | 在应用内使用真实交互式命令行 |
| C06 | 读取 Git 并反映文件代码变化 | 感知本地 Git 状态和内容变化 |
| C07 | GitHub 主要是页面体验参考 | 不因视觉参考自动加入账号、托管和社交功能 |
| C08 | **普通目录亦可登记（v0.2 新增）** | **任何本地目录均可登记为项目，Git 是可选增强能力** |

**C06 与 C07 的工作解释：** 支持只读 Git 集成，不提供提交、拉取、推送和切换分支按钮。这是本稿为协调两项回答采用的边界，待评审确认；用户仍可主动在终端执行 Git 命令。

**C08 的含义（v0.2 关闭的决策）：** 「项目」定义为**已登记的本地目录**，而非「Git 仓库」。Git 状态、差异与分支展示是可选增强能力；目录不是仓库、或 Git 程序不可用时，浏览、文件管理、README 阅读与终端四项能力**全部保留**。产品因此定位为**通用项目入口**，而非仅仓库浏览器。

### 1.2 本稿建议与暂不包含项

以下内容为**设计建议，而非已确认承诺**，待后续决策：

- 默认启动页的选择（见第 10 章）。
- 文件操作的具体边界与批量操作范围。
- 性能目标的具体数值（见 9.1）。

第一版不做：云同步、GitHub 登录、Issues／PR、团队权限、完整代码编辑与调试、插件市场、自动运行项目脚本、整盘项目发现。克隆仓库也不作为登记目录的必要步骤。

## 2. 页面结构：两层首页，一个工作上下文

### 2.1 项目库首页

用于回答「我要继续哪个项目」。展示最近打开、置顶项目、名称／路径搜索，以及「打开文件夹」入口。项目卡片包含名称、简短介绍、本地路径、上次打开时间；同名目录必须以路径区分。

**因 C08 新增：** 项目卡片区分标识是否为 Git 仓库。非 Git 项目显示中性标识（如「文件夹」），不显示分支与变更数量，**不以缺失 Git 呈现为错误状态**。项目库的筛选与排序不因是否为仓库而区别对待。

不在启动时遍历所有项目计算 Git 状态。历史摘要标明更新时间，真正打开项目后再刷新。暂时无法访问的项目保留记录，显示「路径不可用」，提供重新定位和移除记录，不自动删除。

### 2.2 项目首页

采用左侧项目导航、右侧内容、底部可收起终端的结构。

| 区域 | 内容 | 设计目的 |
|---|---|---|
| 项目头部 | 名称、路径、只读分支标识、变更数量、外部打开 | 明确当前项目，降低操作错目录的概率 |
| 概览 | 根目录文件列表；其下展示 README | 保留 GitHub 式阅读顺序 |
| 文件页 | 文件树／面包屑、目录列表或只读文件预览 | 深入浏览时保持目录上下文 |
| 变更页 | 未暂存、已暂存、未跟踪、冲突分组与差异 | 解释本地修改，不提供 Git 写操作 |
| 底部终端 | 当前项目的终端标签与输出 | 浏览、阅读和运行无需切换应用 |

概览和文件页共用同一文件数据与选择状态，避免两套不一致的文件浏览器。进入子目录或文件时切到文件页；返回概览回到项目根目录。README 阅读区域不能因文件数量过多而无限下移，概览文件列表可折叠或限制高度。

**因 C08 新增：** 非 Git 项目的项目头部不显示分支与变更数量，改为显示「未使用 Git」与「初始化 Git」的外部指引（仅说明，不代用户执行）；变更页显示空状态并解释原因，不隐藏入口以免用户误以为功能缺失。

建议第一版采用单窗口、多项目快速切换，每个项目保留独立的页面位置、选中文件和终端。多窗口及任意工作区分屏后置。图标与颜色之外还要显示中文状态文字。

## 3. 项目登记与生命周期

### 3.1 打开与去重

1. 用户通过目录选择器打开项目，验证目录存在且可读。
2. 按真实路径和文件系统身份进行去重；不能简单把所有路径转为小写后比较。
3. 已登记则激活现有记录并更新最近打开时间；首次打开则分配稳定项目 ID。
4. 并行加载目录首屏、README 与 Git 信息；某一能力失败不阻塞其他能力。

**因 C08 新增：** 目录是否为 Git 仓库属于**登记时探测的可选属性**，不作为登记的前置条件，也不产生阻断式提示。探测失败（Git 不可用、权限不足）与「不是仓库」在界面上分别表述，避免把环境问题误报为项目属性。

应用保存用户选择的根目录。若它只是 Git 仓库的子目录，提示「使用所选目录」或「改用仓库根目录」，不静默扩大范围。Git worktree、子模块的识别交给 Git 查询，不假定 .git 一定是文件夹。

### 3.2 记录与磁盘文件分离

「从项目库移除」仅删除应用中的登记、收藏和视图状态，不删除磁盘项目。按钮与确认文案必须明确这一点。若项目有活动终端，先处理会话再移除，不偷偷终止进程。

目录被移动、盘符变化或权限丢失时保留记录。重新定位需由用户选择，并再次核对目录身份；不能凭同名文件夹自动绑定。重新定位到不同位置时重新确认信任状态。

应用级元数据存放在应用数据目录，默认不向用户项目写入配置文件、不改 .gitignore、不初始化 Git。将来若支持项目配置文件，须由用户主动启用。

## 4. README、介绍与文件预览

### 4.1 README 识别规则

建议优先使用用户指定的介绍文件；否则在项目根目录按 README.md、README.markdown、README.txt、无扩展名 README 的顺序查找，识别时兼容名称大小写。根目录未找到时，再检查 docs 和 .github 目录。此优先级是本产品的建议规则，不宣称与 GitHub 完全一致。

存在 README.zh-CN.md 等多语言文件时显示切换入口，不覆盖用户已选版本。第一版内置渲染 Markdown 和纯文本；其他格式提供外部打开。没有 README 时显示空状态和选择介绍文件入口，不擅自生成或写入文件。

项目卡片简介优先使用用户填写的简介，其次提取 README 第一个有效正文段落，跳过标题、徽章、图片与代码块；提取失败回退到路径。第一版不依赖 AI 服务。

### 4.2 浏览与打开

单击选中；双击或 Enter 打开：文件夹进入目录，支持的文件进入只读预览。右键提供「用默认程序打开」「用指定编辑器打开」「在资源管理器中定位」「复制路径」。外部编辑器只列出已配置或已验证可用的程序。

第一版预览 Markdown、纯文本、常见代码和常见栅格图片；代码支持语法高亮与行号，不提供保存按钮。HTML 按源码查看，不执行；SVG 等可携带主动内容的格式不作为普通页面直接加载。可执行文件不因双击预览而运行。

Git 忽略的文件仍可在文件浏览器中找到；忽略规则只影响相应的 Git 状态和后台观察策略，不等于用户无法管理该文件。

### 4.3 安全与异常

README 是不可信内容：禁用脚本和可执行 HTML；相对图片及链接必须经过路径解析，禁止通过符号链接、目录联接或路径穿越静默读取项目外文件。网络图片和徽章默认不加载，用户可按项目允许；外链仅允许明确支持的协议并交给系统浏览器。

建议大文本超过 5 MB、大图片超过 20 MB 时先显示提示，允许受控加载或外部打开；阈值待验证。二进制、编码不支持、文件被占用、无权限分别展示明确状态，不显示空白成功页。

## 5. 文件变化与只读 Git

### 5.1 区分两种「变化」

**文件系统变化**指文件刚被创建、保存、重命名或删除，影响列表和预览刷新；**Git 变化**指它相对于索引或提交基线的差异。文件时间戳变化不必然是代码变更；未保存的编辑器缓冲区也不能通过普通文件监听可靠读取。

外部编辑器保存后，当前预览重新加载并尽量保留滚动位置。文件被删除时保留提示页，提供返回目录；重命名可确认身份时跟随，否则提示用户重新选择，不能猜测。

**因 C08 新增：** 两种变化对非 Git 项目同样成立——文件系统变化与预览刷新完全可用，仅 Git 变化部分不可用。界面须明确区分「没有变化」与「无法判断变化」，后者不得呈现为前者。

### 5.2 状态与差异的表达

| 分组 | 比较对象／含义 | 点击后的内容 |
|---|---|---|
| 未暂存 | 工作区与索引的差异 | 只读逐行差异 |
| 已暂存 | 索引与 HEAD 的差异 | 只读逐行差异 |
| 未跟踪 | 尚未纳入 Git 的文件 | 当前内容，标注没有 Git 历史基线 |
| 冲突 | Git 报告的未合并状态 | 冲突提示与当前内容，不提供自动解决 |

同一文件可以同时已暂存和未暂存。顶部变更数量按去重后的文件数计算，分组数量则分别统计，并在界面解释。重命名按 Git 的检测结果显示，不承诺每次移动都会被判断为重命名。

分支信息只展示，不伪装成可切换控件。处理尚无首次提交、detached HEAD、二进制差异、删除文件及超大差异；不能因无 HEAD 而把整个项目判为损坏。远程链接可选外部打开，但不自动联网 fetch。

### 5.3 刷新机制与失败降级

只对活动项目及必要的 Git 元数据建立受控监听；合并密集事件，异步刷新，回到应用或手动刷新时做状态校验。大型依赖目录不做无边界的内容监听，但用户打开时仍可列出。

Git 是状态事实来源，监听事件只是刷新信号。任务附项目 ID 与递增序号，丢弃过期返回，避免项目 A 的慢查询覆盖项目 B。Git 查询超时、锁冲突或不可用时显示原因与上次更新时间，不能把失败显示成「无变更」。

后台查询建议使用适合程序解析的 porcelain v2 与 NUL 分隔，减少可选索引写锁；不为提速擅自修改仓库配置。未信任仓库的 Git 读取须限制可执行的扩展、外部差异程序及类似回调，具体策略进入安全验证。[1][2]

## 6. 真实终端与会话归属

终端不是命令输出文本框。建议由前端终端组件连接本机伪终端，支持交互式 Shell、Ctrl+C、尺寸变化、滚动缓冲与多标签；Windows 伪控制台负责相应的进程交互。[4][5]

### 6.1 用户行为规则

- 终端由用户明确点击创建，首次使用先确认项目信任；打开目录不自动执行 README、配置文件或 package 脚本。
- 默认从项目根目录启动，可右键「在此目录新建终端」。Shell 可选本机已安装的 PowerShell 或 cmd；Git Bash 等作为后续适配，不假定存在。
- 会话属于创建它的项目。切换项目、收起面板或切换页面不终止进程；也不向原会话静默发送 cd。
- 明确显示「所属项目」和「启动目录」。只有取得可靠 Shell 集成信息时才显示「当前目录」，否则不作虚假展示。
- 关闭终端、关闭项目或退出应用前，提示活动会话及可能中断的工作。不能把「重开 Shell」宣传成恢复了原来的进程。

**因 C08 新增：** 终端能力与目录是否为 Git 仓库无关。非 Git 目录同样可创建终端，且终端是此类项目中使用 Git 命令（如初始化仓库）的正当入口，应用不代为执行。

终端具备当前用户的系统权限，**项目归属不等于文件系统沙箱**。用户可在其中 cd 到项目外；界面上的文件操作保护不能保证阻止用户在终端自行删除文件。应用不默认提权、不代替用户执行命令。

### 6.2 安全与可靠性

终端与不可信 README 预览分离权限和脚本上下文，防止文档脚本接触命令输入。依赖资源随应用打包，避免向终端页面动态注入远端脚本；不默认记录终端输入或持久化敏感输出。[3][4]

限制内存中的回滚行数，对高频输出做缓冲与背压。Shell 启动失败保留错误信息并允许重试；关闭时管理会话和附接进程，不承诺自动清理所有自行脱离的后台进程。重启应用默认恢复项目视图，而非自动重跑旧命令。

## 7. 基础文件管理与保护规则

第一版建议包括：新建空文件／文件夹、重命名、复制、剪切粘贴及删除。操作以项目内路径为主；跨项目、跨卷移动及文件夹合并先交给系统资源管理器，避免把完整文件管理器的边界一次性带入。

| 场景 | 建议处理 |
|---|---|
| 同名冲突 | 显示源和目标，支持取消、跳过或保留两份；不静默覆盖 |
| 删除文件／目录 | 列出相对路径和数量，明确发送到系统回收站；不可回收则停止并说明 |
| 重命名／移动 | 操作前验证最新状态；成功后同步列表、预览和 Git 状态 |
| 文件被占用／无权限 | 保留源文件，报告具体失败，不默认请求管理员权限 |
| 批量操作部分失败 | 逐项记录成功、失败与未执行项，不能只给统一成功提示 |
| 项目根目录或 .git 元数据 | 不从普通文件操作菜单提供破坏性操作 |

文件变更与磁盘确认成功后才更新界面；不提供无法真正完成的「撤销」。删除后的恢复可指引系统回收站。建议所有写操作在信任项目中启用，不可信项目默认只读浏览。

## 8. 技术架构与数据模型建议

### 8.1 模块划分

界面层只描述用户操作；通过带类型和来源校验的进程间通信调用本地服务。建议拆成项目登记、文件访问、Markdown 预览、Git 查询、文件监听、PTY 会话六个模块。文件系统事件、Git 快照和终端输出走不同通道，避免互相阻塞。

特权服务根据项目 ID 和相对路径检查权限及真实路径，不信任前端传来的任意绝对路径。检查需考虑目录联接、符号链接和检查到执行之间的路径变化。Git 调用以参数数组启动，禁止拼接用户路径成为 Shell 命令。终端输入是用户明确使用的独立特权通道，不能开放给文档预览。

### 8.2 技术路线：对比与建议（v0.2 新增）

#### 8.2.1 本项目的真实难点排序

选型应以本项目的实际风险为准，而非框架的通用标签。四项难点按权重排列：

| 权重 | 难点 | 具体内容 |
|---|---|---|
| 1 | 真实终端（PTY） | 交互式 Shell、Ctrl+C、尺寸变化、多会话、背压、进程生命周期 |
| 2 | 不可信内容隔离 | README 预览与终端必须分离权限与脚本上下文 |
| 3 | Windows 路径身份与文件操作 | 去重、大小写、目录联接、回收站 |
| 4 | 只读 Git 查询 | porcelain v2 解析、超时与锁冲突降级 |

#### 8.2.2 候选对比

**Electron + React + TypeScript**

| 维度 | 说明 |
|---|---|
| 终端 | node-pty 在 Windows 上通过 ConPTY 工作，是该问题的成熟方案，已被大规模验证 |
| 语言 | 主进程、预加载层、渲染层统一为 TypeScript，IPC 契约可共用同一套类型定义 |
| 系统能力 | child_process（Git 调用）、fs、shell.trashItem（回收站）、shell.openPath（外部打开）均为内置 |
| 排错 | 生态与先例最丰富，未知问题的解决路径明确 |
| 代价一 | 分发体积显著较大（含运行时） |
| 代价二 | 内存与冷启动开销相对更高 |
| 代价三 | 隔离默认不安全，必须显式配置 contextIsolation、sandbox、关闭 nodeIntegration 并校验 IPC 来源 |

**Tauri v2 + Web 前端 + Rust 服务**

| 维度 | 说明 |
|---|---|
| 体积 | 分发体积可小一个数量级，复用系统 WebView |
| 权限 | capability／permission 为声明式权限模型，默认拒绝，隔离强度更高 |
| 资源 | 后端内存占用通常更低 |
| 代价一 | 终端需自建：从 PTY 读取、序列化、IPC 传输、渲染到背压控制的完整链路都要自行设计 |
| 代价二 | 双语言栈，IPC 契约需在两侧各自维护 |
| 代价三 | Windows 依赖 WebView2 运行时，受限环境需额外引导安装 |
| 代价四 | 生态较新，排错成本高 |

#### 8.2.3 建议

**建议采用 Electron + React + TypeScript。**

依据：本项目权重最高的难点是真实终端，Electron 在该项上具有成熟方案；其隔离短板属于「已知且可配置」的范畴，有官方安全指南可循，不构成结构性障碍。

**改用 Tauri 的触发条件：** 分发体积成为硬性约束，或团队已具备 Rust 能力并看重声明式权限模型，则应重新评估。

**该判断须在 M0 技术验证获得实测数据后复核，而非仅凭框架标签决定。** 终端原型中的 PTY 会话管理与流控逻辑在两条路线间可部分复用，先行验证不构成浪费。[6]

### 8.3 最小数据对象

- Project：稳定 ID、显示名称、原始路径、规范化身份、简介覆盖、README 选择、置顶、最近打开时间、信任状态、**是否为 Git 仓库（v0.2 新增，可选探测属性）**。
- ProjectViewState：项目 ID、当前页面、相对路径、滚动位置、终端面板尺寸。
- GitSnapshot：项目 ID、查询序号、分支、状态项、更新时间、错误／过期状态；不作为永久事实。
- TerminalSession：会话 ID、项目 ID、Shell、启动目录、进程句柄、运行状态；只在本次运行有效。

Git 快照和终端输出不默认长期保存；诊断日志避免记录文件正文、完整命令输入与环境变量秘密。

### 8.4 存储选择

建议本地 SQLite 保存应用元数据，源码仍留在原目录；也可在极小原型阶段使用具备安全写入机制的配置文件。持久化选择待实现评审。

## 9. 第一版验收与实施顺序

### 9.1 可验证验收场景

1. 打开同一路径两次只产生一条项目记录；应用重启后记录仍在；移除记录后磁盘文件仍在。
2. 无 README、无 Git、Git 程序不可用分别降级，文件浏览与终端入口仍可用。
3. README 的项目内相对图片可正确显示；脚本、项目外路径和默认未授权网络资源被阻止。
4. 在外部编辑器保存文件后，预览与 Git 状态更新；已暂存后再次修改的文件在两个分组中正确出现。
5. 文件名含中文、空格、特殊字符及大小写变化时，浏览和 Git 路径不会串行或错配。
6. 切换项目时原终端进程仍运行，新项目不接收原项目输出；退出前明确提示会话影响。
7. 重命名冲突、锁定文件、回收站不可用、部分批量失败不造成静默覆盖或源文件丢失。
8. 大目录、超大文件、高频终端输出和 Git 超时不会冻结主界面；旧请求结果不会覆盖新项目。
9. **（v0.2 新增，因 C08）** 登记一个非 Git 目录：卡片与项目头部不以错误状态呈现；文件浏览、README、终端全部可用；变更页给出明确的「未使用 Git」解释而非空白。

初始性能目标建议：100 个登记项目的项目库冷启动在 3 秒内可操作；含 1,000 项的目录首屏在 1 秒内可见；普通项目保存稳定后约 2 秒内完成状态刷新。**这些是待验证目标，不是测试结果**；需要在确定硬件、磁盘和仓库基线后修订，超限时必须有加载状态及取消机制。

### 9.2 按可验收结果推进

- 技术验证：优先验证真实终端、Markdown 隔离、文件回收站与 Git 差异解析，排除基础边界问题。
- 里程碑一：项目登记、项目库首页、项目概览、README 与只读预览。
- 里程碑二：外部保存感知、只读 Git 状态与差异、真实项目终端。
- 里程碑三：基础文件操作、异常处理、Windows 分发与完整回归验收。

第一版之后再考虑：标签分组、常用文档收藏、用户确认后执行的命令收藏、跨项目内容搜索、多窗口和 Git 写操作。AI 功能不是当前主流程的前置条件。
